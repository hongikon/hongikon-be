# 물어보기 — 규정 그래프(고른 안내의 이웃 규정을 함께 읽히기) 설계

작성 2026-10-30. 상태: 설계(구현 전). 앞 문서: [`ask-embedding-plan.md`](ask-embedding-plan.md)(RAG 검색), [`ask-reasoning-eval.md`](ask-reasoning-eval.md)(추론형 평가, 6절 '규정 그래프').

## 1. 왜 하나

- 추론형 평가(10-28)에서 Opus 5.5 로 올려도 남은 실패의 절반이 **결과 누락**이다. 안내 원문에는 사실이 있는데 답에 빠진다.
  - "연속 성적경고 → 휴학 → 학기재수강하면 경고도 없어지지?" — 학기재수강 안내는 찾지만 '경고는 유지, 휴학은 연속을 끊지 않음, 한 번 더면 제적'을 놓친다.
  - R02·R24 두 갈래 중 하나만 말함, R11 장학생이면 결론이 바뀌는데 빠뜨림.
- 검색으로는 풀리지 않는다. 이웃 규정(성적경고·제적)은 질문 낱말과 뜻이 멀어서 bge-m3·BM25 상위에 오지 않는다. 질문에 '경고'가 없어도 읽혀야 한다.
- 모델에게 "다른 규정도 찾아라"고 시키는 것도 답이 아니다. Haiku 추론형 지시는 공지를 더 찾다 날짜에 매달려 34% 로 떨어졌다(원인 3).

→ 규정 사이의 관계(결과·선행조건·예외)를 미리 적어 두고, **고른 안내가 정해지면 서버가 그 이웃을 정해진 규칙으로 함께 넘긴다.**

## 2. 하지 않는 것

| 방식 | 하지 않는 이유 |
|---|---|
| 일반 GraphRAG(원문 전체에서 LLM 으로 개체 추출 + 커뮤니티 요약) | 전역 요약 질문용이다. 우리 실패는 규정 몇 개 사이의 연결이다. 만들기 비싸고 틀린 선이 드러나지 않는다. |
| 모델이 부르는 그래프 도구(`get_related_rules`) | 모델이 놓친 걸 모르니 부르지 않는다(같은 자리에서 또 실패). 부를 때마다 LLM 왕복이 늘고 실행마다 흔들린다. 상위 모델 전용 보조로만 나중에 검토. |
| 처리 흐름 그래프(상황 정리 → 되묻기 → 검증 분기) | 다음 단계. 이 그래프의 `condition` 칸이 그 분기의 기준이 된다(9절). |
| 그래프 DB | 점 50~100개. JSON 파일 하나로 충분하다. |

## 3. 구조

```
질문 → ② 찾기(RAG, 지금 그대로) → ③ 고르기(지금 그대로) → answerIds
                                                         │
                                  [새로] 규정 그래프: answerIds → 점 → 이웃 1~2단계
                                                         │
                     [함께 볼 규정] 블록(선의 사실 문장 + 근거) + 이웃 안내 원문(최대 2)
                                                         ↓
                                                  ④ 답 쓰기(지금 그대로)
```

- 끼우는 곳: `AskRouteService.route()` — `anchorsFor()` 로 `answerIds` 가 정해지고 `progress.picked()` 한 뒤, `answerContext()` 를 만들기 전.
- RAG 와 독립이다. `ask.rag.enabled=false` 여도 분류가 고른 안내에서 출발해 동작한다.
- 새 클래스 `AskRuleGraph`(파일 읽기·검사·이웃 찾기). `AskRouteService` 는 결과 블록을 context 에 붙이고 이웃 안내 ID 를 `answerIds` 뒤에 더한다.

## 4. 데이터: `src/main/resources/ask/rule-graph.json`

```json
{
  "version": "2026-10-30.1",
  "catalogVersion": "<만들 때의 catalog.json version>",
  "nodes": [
    { "id": "semester-retake", "name": "학기재수강",
      "guides": ["faq-retake/semester-retake-range", "faq-retake/semester-retake-apply", "faq-retake/semester-retake-after"] },
    { "id": "academic-warning", "name": "성적경고", "guides": ["<성적경고 안내 id>"] },
    { "id": "expulsion", "name": "제적", "guides": ["<제적 안내 id>"] },
    { "id": "leave", "name": "휴학", "guides": ["leave-of-absence/general", "leave-of-absence/limits"] }
  ],
  "edges": [
    { "from": "semester-retake", "to": "academic-warning", "type": "결과",
      "fact": "학기재수강을 해도 이미 받은 성적경고는 없어지지 않는다.",
      "guide": "<근거 안내 id>", "quote": "<근거 안내 원문에 있는 문장 그대로>",
      "condition": null, "reviewed": "2026-10-xx 운영진" },
    { "from": "leave", "to": "academic-warning", "type": "예외",
      "fact": "휴학한 학기는 연속 성적경고를 끊지 않는다.",
      "guide": "<근거 안내 id>", "quote": "<원문 문장>", "condition": null, "reviewed": "…" },
    { "from": "academic-warning", "to": "expulsion", "type": "결과",
      "fact": "성적경고를 연속 3회 받으면 제적된다.",
      "guide": "<근거 안내 id>", "quote": "<원문 문장>", "condition": null, "reviewed": "…" }
  ]
}
```
(위 사실·id 는 모양 예시다. 실제 문장은 원문에서 뽑고 운영진이 확인한다.)

### 선 종류

| type | 뜻 | 예 |
|---|---|---|
| 결과 | A 를 하면/되면 B 가 생긴다 | 학기재수강 → 성적경고 유지, 성적경고 3회 → 제적 |
| 선행조건 | A 를 하려면 먼저 B | 전과 → 지원 자격(이수 학기) |
| 예외 | B 가 A 의 일반 규칙을 바꾼다 | 장학생 → 휴학 시 장학 처리 |
| 제한 | A 에 횟수·학점·기간 상한 | 휴학 → 최대 학기 수 |
| 기간 | A 의 신청·처리 시점 규칙(날짜 자체는 공지에서) | 자퇴 → 등록금 반환 비율(개강일 기준 일수) |

### 칸 규칙

- `fact`: 한 문장. 답 쓰기에 그대로 들어간다.
- `guide` + `quote`: **근거는 `sources.json` 안내 원문만.** `quote` 는 그 안내 원문에 글자 그대로 있어야 한다(4-1 검사).
  - 공지 Q&A 에만 있는 사실(예: 수강정정허가원, R42)은 먼저 안내 원문에 보강하고(평가 원인 7) 그다음 선을 잇는다. '[안내 원문]만 근거' 원칙을 깨지 않는다.
- `condition`: 선이 맞으려면 필요한 학생 상황. 정해진 칸 이름만 쓴다 — `학년`, `이수학기`, `휴학중`, `장학생`, `분할납부`, `군복무`, `졸업유예`.
  예: `{ "장학생": true }`. 질문에서 그 칸을 알 수 없으면 답 쓰기가 갈리는 기준을 보이고 되묻는다.
- `reviewed`: 사람이 확인한 날짜(`YYYY-MM-DD`)·사람. **비어 있으면 서버가 읽지 않는다.**

### 4-1. 불러올 때 검사(`AskRuleGraph`)

- 선의 `guide` 가 카탈로그에 없으면 그 선을 버린다.
- `catalogVersion` 이 지금 카탈로그와 다르면 선마다 `quote` 가 `catalog.source(guide)` 에 그대로 있는지 본다. 없는 선만 버린다(그래프 전체를 끄지 않는다).
- 버린 선은 시작 로그에 개수와 id 를 남긴다. 버린 선이 전체의 20% 를 넘으면 경고.

## 5. 서버 동작

1. 출발점: `answerIds` 각 안내 → 그 안내를 `guides` 에 가진 점들.
2. 이웃 찾기:
   - 1단계: 출발점에서 나가는 모든 선 + 출발점으로 들어오는 `예외`·`제한` 선(출발 규칙을 바꾸는 것).
   - 2단계: 1단계에서 `결과` 선으로 간 점에서 다시 `결과` 선만(경고 → 제적 같은 사슬).
   - 3단계 이상은 가지 않는다.
3. 자르기: 선은 최대 8개(`ask.graph.max-edges`). 순서는 단계(1 먼저) → 종류(결과 > 예외 > 제한 > 선행조건 > 기간).
   이웃 안내 원문은 1단계 `결과`·`예외` 선의 근거 안내만 최대 2개(`ask.graph.max-guides`) `answerIds` 뒤에 더한다 — 나머지는 선의 사실 문장만.
4. 답 쓰기에 붙이는 블록(context 끝):
   ```
   [함께 볼 규정] 고른 안내와 이어진 규정이다. 학생 상황에 해당할 때만 결론과 결과에 반영한다.
   - 학기재수강 →(결과) 성적경고: 학기재수강을 해도 이미 받은 성적경고는 없어지지 않는다. (근거: faq-…)
   - 성적경고 →(결과) 제적: 성적경고를 연속 3회 받으면 제적된다. (근거: …)
   - 휴학 →(예외) 성적경고: 휴학한 학기는 연속 성적경고를 끊지 않는다. (근거: …)
   - 휴학 →(예외) 장학: … (조건: 장학생 — 질문에서 알 수 없으면 갈리는 기준을 보이고 묻는다)
   ```
5. 답 쓰기 지시(`ANSWER_SYSTEM`)에 세 줄 추가:
   - [함께 볼 규정]은 학생 상황에 해당할 때만 쓴다. 해당 없는 규정을 늘어놓지 않는다.
   - 해당하면 결론 문장에 반영하고(예: "경고는 그대로예요"), 근거 안내 id 를 근거로 짚는다.
   - 조건 칸을 질문에서 알 수 없고 그 조건으로 결론이 갈리면, 갈리는 기준을 보이고 되묻는다.
6. 근거 표시: 답이 짚은 이웃 안내는 지금처럼 `sourceIds` 로 앱에 링크된다. 짚지 않은 이웃은 나가지 않는다.
7. 기록: `AskTrace` 에 쓴 선 id 목록을 남긴다(평가·디버깅용, 질문 글과 별도 저장 안 함).
8. 설정: `ask.graph.enabled=${ASK_GRAPH_ENABLED:false}`, `ask.graph.max-edges=8`, `ask.graph.max-guides=2`. 파일이 없거나 읽기에 실패하면 꺼진다(지금 방식 그대로).

## 6. 만드는 법

- 범위(1차): 휴학·복학·학기재수강·재수강·군휴학·전과·자퇴, 그리고 이들이 닿는 결과 규정(성적경고·제적·등록금 반환·장학·졸업). 점 50~100개.
- 순서:
  1. 후보 뽑기 — FE `scripts/ask/graph/extract.mjs`: 범위 안내 원문(`sources.json`)을 Claude 에 주고 선 후보를 JSON 으로. `quote` 필수, 원문에 없는 말은 내지 않게.
  2. 자동 검사 — `scripts/ask/graph/validate.mjs`: `quote` 원문 포함, `guide` 존재, 같은 선 중복, 끊긴 점, `condition` 칸 이름.
  3. 사람 검토 — 운영진이 선마다 맞음/틀림/고침. 맞은 선만 `reviewed` 를 채운다. **틀린 선 하나가 곧 손해 오류**라 이 단계는 빼지 않는다.
  4. BE `src/main/resources/ask/rule-graph.json` 으로 내보내기.
- 유지: `export-catalog` 로 `sources.json` 이 바뀌면 `validate.mjs` 를 돌린다. `quote` 가 깨진 선은 재검토 목록으로. 학기마다 학사 규정 개정 공지가 나오면 해당 점을 다시 본다.

## 7. 평가

- 시험지: FE `scripts/ask/cases-reason/reason.json` 44문항(그대로). 함께: 기준 정답표 32, 학과 공지 정답표 40, 범위 밖 21.
- 설정(각 3회 반복, 평균과 흔들림):

| 설정 | 모델 | 그래프 |
|---|---|---|
| haiku-base | Haiku 5.5 | 끔 (기준) |
| haiku-graph | Haiku 5.5 | 켬 |
| sonnet-graph | Sonnet 5.5 | 켬 |
| opus-reason | Opus 5.5 | 끔 (10-28 결과, 비교용) |

- 지표: 원인 1(결과 누락) 수, 핵심 사실(must) 포함률, 손해 오류(mustNot), 되묻기 3/3, 범위 밖 21/21, 답 쓰기 입력 토큰·질문당 비용·지연.
- 바꿔 탈 기준:
  - 결과 누락이 기준의 절반 이하, 핵심 사실 포함률 +10%p 이상.
  - 손해 오류 0, 되묻기·범위 밖 유지, 기준·학과 공지 정답표에서 지금보다 낮지 않다(±1 흔들림 안).
  - 질문당 입력 토큰 증가 30% 이하.
- 기대: haiku-graph 또는 sonnet-graph 가 opus-reason 에 가까우면, 모델을 올리지 않고 결과 누락을 줄인다(질문당 $0.19 → Sonnet·Haiku 수준).

## 8. 위험과 막는 법

| 위험 | 막는 법 |
|---|---|
| 틀린 선 → 틀린 결론(손해 오류) | `quote` 원문 대조, 사람 검토 필수, `reviewed` 없으면 안 읽음. 다음 단계의 검증 단계와 겹쳐 막는다. |
| 해당 없는 규정까지 늘어놓음(답이 길어짐) | "해당할 때만" 지시, 선 8개·이웃 원문 2개 상한, 답 길이를 지표로 잰다. |
| 규정 개정으로 낡은 선 | 카탈로그가 바뀌면 `quote` 검사로 깨진 선 자동 제외, 재검토 목록. |
| 입력이 커져 비용·지연 증가 | 사실 문장 위주(원문은 최대 2개), 입력 토큰을 지표로. |
| 개인정보 | 규정만 담는다. 학생 상황은 질문에서만 읽고 그래프에 저장하지 않는다. |

## 9. 다음 단계와 이어지는 곳

- 상황 정리 단계(평가 6절): 답 쓰기 전에 질문에서 `condition` 칸(학년·휴학중·장학생…)을 뽑는다. 쓰려는 선의 조건 칸이 비면 규칙으로 되묻기 → 되묻기를 모델 판단에서 서버 분기로 옮긴다.
- 검증 단계: 답의 결론·숫자를 [안내 원문]과 선의 `quote` 에 대조.
- 모델 나눠 쓰기: 그래프가 `결과` 선으로 성적경고·제적·등록금에 닿는 질문만 상위 모델로 보낸다(위험 주제 판정 기준으로 재사용).

## 10. 사람이 직접 해야 하는 일

코드·스크립트·평가 실행은 자동화할 수 있다. 아래는 **사람의 판단이 필요해서 맡길 수 없는 일**이다.

| # | 할 일 | 누가 | 언제 | 왜 사람이어야 하나 |
|---|---|---|---|---|
| 1 | 1차 범위 확정 — 어떤 규정부터(6절 범위 그대로 갈지, 등록금·장학을 넣을지) | 운영진 | 시작 전 | 학생 질문에서 무엇이 중요한지는 운영 판단 |
| 2 | 선 종류 5개·`condition` 칸 이름 목록 확정 | 운영진 + 개발 | 시작 전 | 나중에 바꾸면 선 전체를 다시 검토해야 한다 |
| 3 | **선 검토** — 뽑힌 후보마다 맞음/틀림/고침, `reviewed` 채우기 | 학사 규정을 아는 운영진 | 후보 뽑은 뒤(1~2일) | 틀린 선 = 손해 오류. 가장 중요하고 맡길 수 없다 |
| 4 | 애매한 규정 확인 — 원문끼리 어긋나거나 FAQ 에만 있는 사실은 학사지원팀 공지·FAQ 로 확인 | 운영진 | 검토 중 | 공식 근거 판단 |
