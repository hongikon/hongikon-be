# 물어보기 — 임베딩 검색(로컬 모델)으로 바꾸기 계획

작성 2026-10-28. 상태: 로컬에서 RAG 켜고 확인 완료(dev). 운영은 터널 연결 뒤.

## 1. 왜 바꾸나

지금 안내를 찾는 길은 세 가지다.

1. 앱 낱말 찾기: `topics/*.py` 에 손으로 적은 낱말 목록. 질문에 그 낱말이 있으면 그 안내를 '후보(hint)'로 서버에 보낸다.
2. 서버 1차 고르기: Claude 가 안내 773개의 한 줄 요약(카탈로그, 약 6만 자)을 통째로 읽고 고른다. 요약 끝 꼬리표(#낱말)는 1의 낱말 목록에서 나온다.
3. 답 쓰기: 고른 안내 원문만 보고 답한다. 부족하면 `search_guides`(낱말 점수)·`search_notices`·`search_facilities` 로 더 찾는다.

3은 RAG 구조다. 문제는 찾는 단계가 손으로 적은 낱말과 낱말 점수에 기대고 있다는 것이다.

- 안내를 하나 넣을 때마다 낱말 목록을 새로 짜야 한다. 안내가 늘수록 서로 부딪힌다. 낱말 찾기 정답표가 2,749문항까지 늘어난 것도 이 충돌을 막으려고였다.
- 10-27 사례:
  - '컴공 전필 뭐야'가 꼬리표 낱말 순서 때문에 적용원칙 안내로 갔다.
  - '전필 안 해도 졸업?'은 hint 가 있을 때와 없을 때 답이 달랐다.
- 운영진 결정(10-27): 낱말을 채팅으로 손수 할당하는 방식은 그만둔다. 미리 계산해 둔 원문 색인에서 바로 찾는다.

## 2. 바꿀 구조

```
[원문] 학교 페이지·교과과정책자·학과 규정(scripts/ask/data) ─┐
                                                          ├─ 문단 자르기 → 임베딩(맥미니에서 미리 계산) → 색인 파일
[공지] news 테이블(매시간 수집) ───────────────────────────┘    공지는 서버에서 새 글만 계산

질문 → (서버) 임베딩 서버로 질문 벡터 → 색인에서 가까운 문단 + 낱말 검색(BM25) 순위 합치기
     → 상위 문단을 Claude 에 [안내 원문]으로 → 지금처럼 원문 안에서만 답
```

- 임베딩 서버: 문장을 벡터로 바꾸는 작은 서버. 운영 EC2 안에서만 돌고 밖으로 열지 않는다(127.0.0.1).
  - 질문이 외부 임베딩 업체로 나가지 않는다 → 개인정보처리방침 국외 이전 항목이 늘지 않는다(Anthropic 만 그대로).
  - 질문마다 추가 비용이 없다.
- 고유명사(과목번호·학번·건물 기호)는 뜻 검색이 약하다. 그래서 낱말 검색(BM25)과 순위를 합친다(RRF). 낱말 검색도 로컬이다.
- 손으로 짠 낱말 목록·꼬리표·앱 hint 는 없앤다.
  - 정답표는 버리지 않는다. '맞는 문단을 꺼냈나' 채점용으로만 쓴다.
  - 운영진이 다듬은 안내 카드(askAnswers.ts)는 원문 문단과 같이 색인한다.

## 3. 실험(로컬, 맥미니 M1)

- 원문: 백엔드 `ask/sources.json` 안내 773개(약 136만 자). 600자 안팎 문단으로 자르고, 안내 첫 줄(제목·요약)을 문단 앞에 붙인다.
- 비교: BM25(한글 2글자 단위), multilingual-e5-small, bge-m3, 각 모델 + BM25 혼합.
- 채점:
  - 낱말 찾기 정답표: 정답 안내가 상위 k개 안에 있나(R@k). 낱말 찾기에 맞춰 만든 문항이라 지금 방식이 유리하다는 점을 감안한다.
  - 기준 정답표(32): 정답 안내 R@k, 그리고 꼭 들어가야 할 사실(must)이 상위 문단 8개 안에 다 있나.
- 결과(검색만, 10-28):

| 방식 | 정답표 R@10 | 기준 R@5 | 기준 사실 포함(상위 8문단) |
|---|---|---|---|
| BM25 | 78.3% | 65.4% | 24/26 |
| multilingual-e5-small | 85.5% | 84.6% | 24/26 |
| bge-m3 | 89.8% | 92.3% | 25/26 |
| bge-m3 + BM25(RRF) | 90.6% | 88.5% | 26/26 |

→ bge-m3 + BM25 를 쓴다. 색인 만들기 CPU 17분(2,366문단). 질문 하나 임베딩 0.25초 안팎(CPU).

- 결과(서버 답 전체, 로컬, 같은 날 같은 데이터):

| | RAG 끔(지금 방식, 앱 hint 있음) | RAG 켬(hint 무시) |
|---|---|---|
| 기준 정답표 핵심 조건 | 30/32 | 29/32 |
| 학과 공지 정답표 | (10-25 35~36/40) | 34/40 |
| 범위 밖 거절 | — | 21/21, 잘못 거절 0 |

  - RAG 가 놓친 것: '최소 몇 학점'(졸업학점 안내를 고름), 'F 과목 재수강 개수'(답에서 '제외' 표현이 빠짐 — 답 쓰기 흔들림).
  - 지금 방식이 놓쳤는데 RAG 가 맞힌 것: '계절학기 최대 몇 학점'. 둘 다 놓친 것: 계절학기 학점당 금액.
  - '전필 안 해도 졸업?'은 hint 없이도 적용원칙을 찾는다(지금 방식은 hint 없으면 단과대학 요건으로 갔다).
  - 판정: 손으로 적은 낱말 없이 같은 수준 → dev 에서 RAG 를 켠다.

## 4. 만든 것(10-28)

- `tools/embed-server/`: server.py(임베딩 서버, 키 필수, 127.0.0.1), build_index.py(색인), run.sh·launchd.plist.template(맥미니 자동 실행), README.
- `AskEmbedClient`(임베딩 서버 호출), `AskRetriever`(색인 읽기·bge-m3 내적 + BM25 → RRF, 안내로 묶기).
- `AskRouteService`: RAG 가 켜져 있으면 분류 전에 검색 후보 6개를 찾아 앱 hint 대신 분류에 준다. 분류가 아무것도 못 고르면 후보 앞 2개로 답한다.
- `search_guides` 도구도 RAG 검색으로.
- 설정 `ask.rag.*`(기본 끔). 임베딩 서버 실패 → 503(앱은 실패를 알린다).

## 4-1. 학과 홈페이지(10-28)

- 운영진 요청: 학과 홈페이지 내용도 찾게. FE `scripts/ask/depthome.py` 가 학과 홈페이지 35곳 메뉴 페이지를 모아 `data/rag-depthome.json`(94쪽 — 본문 46·위치만 48)에 둔다.
  - 게시판(공지는 서버가 따로 모은다)·조교/연구실/동문/갤러리 쪽은 뺀다. 이메일은 지운다.
  - 화면에서 채우는 틀('{{ }}'), 여러 학과에 같은 공통 문구도 지운다.
- 낱말 목록 없이 원문 그대로 색인한다. build_index.py 가 'page:<key>' 문단으로 함께 넣는다: 2,366 → 2,592문단.
  - 서버는 맨 앞 10문단 안에 든 홈페이지 쪽(최대 2)을 답 쓰기에 원문으로 넘기고, 쓰면 그 학과 홈페이지 링크를 붙인다.
- 개인정보 거르기(10-29 공개 저장소 점검): 학번이 있는 줄(명예의 전당 실명·학번), 게시판 목록(글 제목 속 학생 실명)은 빼고, 교수·교직원·연구실 소개는 위치만. 휴대전화 번호는 FE gen.py 가 지운다.
- 교수 정보(운영진 결정): 교수 소개 페이지는 내용을 넣지 않고 '어느 학과 홈페이지 어느 메뉴에 있다'만 넣는다(linkOnly).
  - 답 규칙: 교수 개인 연구실·전화·이메일·면담은 원문에 있어도 쓰지 않고 그 페이지로 안내한다.
  - 10-31 바꿈(운영진 결정): 교수진 페이지는 **이름·소속(학과)·직위·연구분야**만 넣는다(FE `depthome.py --faculty`,
    헤드리스 Chrome 으로 화면을 그려 세 칸만 읽는다 — 목록이 자바스크립트로 채워진다). 32쪽·700명.
    학위·출신 학교·연구실·전화·이메일·사진은 읽지도 저장하지도 않는다. 교직원·연구랩·조교 소개와 목록 형식이 아닌 쪽은 위치만.
    답 규칙도 '이름·소속·직위·연구분야는 답해도 되고, 연락·면담은 교수진 페이지로'로 바꿨다.
- 확인(로컬):
  - '신소재 실험과목 몇 개' → 2과목(신소재 홈페이지 졸업요건 링크)
  - '컴공 ○○ 교수님 연구실' → 교수진소개 링크로 안내
  - '실용음악전공 졸업요건' → 전공 50·총 132학점·졸업공연(실용음악 홈페이지)
- 저작권·개인정보 검토(10-28 운영진과): 공개 페이지·robots.txt 준수·1초 간격, 요약과 출처 링크, 비공식 표시.
  - 남은 일: 학교에 알리고 동의받기 권장. 공지 속 학생 개인정보(장학생 명단 등) 거르기.

## 6. 운영 반영 전에 정할 것

- 임베딩 서버 자리: 맥미니(10-28 운영진 결정). 맥미니나 집 인터넷이 멈추면 물어보기도 503 이 된다 — 앱은 실패를 알린다.
- 연결: 사설 터널(Tailscale 등)만 쓴다. 공인 포트는 열지 않는다. 임베딩 서버는 터널 주소에만 열고 키를 확인한다.
- 개인정보: 질문 글이 운영 서버 → 맥미니로 간다(국외 이전 아님). 처리방침의 처리 위치 설명은 반영 전에 확인한다.
- 바꿔 탈 기준:
  - 기준 정답표·학과 공지 정답표에서 지금 방식보다 낮지 않다(위 표: 29 대 30 은 실행마다 ±1 흔들림 안).
  - 범위 밖 질문 거절 21/21 을 유지한다.
